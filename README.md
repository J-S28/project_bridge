# Project Bridge

**AI-powered citizen participation and governance platform** — built for the *People's Priorities: AI for Constituency Development Planning* hackathon (Build with AI / Hack2Skills).

- **Live demo:** https://project-bridge-eight.vercel.app
- **Repo:** https://github.com/J-S28/project_bridge
- **Demo accounts:** see [`DEMO_LOGINS.md`](./DEMO_LOGINS.md)

## The problem

MPs and MLAs get development requests through scattered channels — meetings, letters, grievance portals, social media — with no way to consolidate them, spot recurring needs, or weigh competing proposals against real demand data (e.g. a request for school upgrades vs. actual enrollment and travel-distance numbers).

## The solution, in one paragraph

Citizens report civic issues in plain language — by typing or by **speaking in any language** (English, Hindi, Telugu, Tamil tested), with a photo and location. Gemini classifies each report (department, category, priority, sentiment), writes a short summary, checks it against nearby open complaints to **consolidate duplicates into a single tracked issue with a rising report count**, and decides whether it's a routine fix or something that needs budget/infrastructure — in which case it's flagged for the elected representative, not just the department. Non-digital grievances — letters, phone calls, public meetings — are digitized into the same pipeline by an **Office Staff** role, so a rep's team has one intake system instead of a spreadsheet plus an app. Officers work routine cases through a restricted status pipeline, but **only the citizen can close a case** — officers submit proof of work, the citizen confirms it or reopens it. Above the officer sits a real accountability hierarchy — **department head → MLA → MP** — each seeing only what's escalated to their tier, either because it needs funding/infrastructure or because it's been sitting too long. Representatives also get a **ward-level demand hotspot map and priority heatmap** (color-coded by severity, no map-tile billing required) and an **AI-ranked list of development priorities**, generated by comparing citizen suggestion volume against seeded demographic/infrastructure-gap data — the platform's actual core differentiator over a typical ticket router.

## Roles & escalation hierarchy

| Role | Scope | Sees |
|---|---|---|
| **Citizen** | themselves | their own submitted complaints; confirms/reopens resolved ones |
| **Office Staff** | attached to a department/MLA/MP office | logs grievances from letters, phone calls, meetings, and walk-ins into the same pipeline; sees what they've logged |
| **Officer** | one department, one ward | that ward's complaints for their department; restricted status buttons |
| **Department Head** | one department, one MP constituency (all wards under it) | cases stuck past the officer's SLA, before MLA/MP see them |
| **MLA** | one ward | department breakdown, priority heatmap, AI insight, priority ranking, escalated cases (level ≥ 2), for their ward |
| **MP** | one constituency (multiple wards) | same as MLA but constituency-wide, plus a ward-by-ward comparison table, a demand hotspot map, and a dedicated "needs funding/infra decision" queue |

Escalation is **computed at read time**, not stored or cron-driven — a pure function of how long a complaint has sat since its last update versus a priority-based threshold (Critical: 24h, High: 72h, Medium: 7 days, Low: 14 days). See [`lib/escalation.ts`](./lib/escalation.ts). This is layered with a second, independent signal — `ai.escalateToRepresentative`, decided by Gemini at classification time, for issues that need budget/capital infrastructure regardless of how long they've been open.

## Data model

Core types live in [`lib/types.ts`](./lib/types.ts):

- **`AppUser`** — `role` (`citizen | officer | department_head | mla | mp | office_staff`), plus `department`/`state`/`constituency`/`officeType` depending on role
- **`Complaint`** — citizen's raw text, `type` (`Grievance` | `Suggestion`), `location` (lat/lng, state, ward, `constituencyMP`), the Gemini-produced `ai` classification, `status`, a full `history` array of status transitions (including officer proof photos), `source` (`Citizen App | Letter | Phone Call | Public Meeting | Walk-in | Email | WhatsApp | Existing Government Portal`), and consolidation fields `clusterId` / `reportCount` / `reportedByCitizenIds` for merged duplicates
- **`AIClassification`** — department, category/subcategory, priority, sentiment, a ≤25-word summary, `escalateToRepresentative` + reason, confidence, `duplicateOfId` when Gemini matches an existing nearby open complaint

Firestore security rules (`firestore.rules`) enforce the hierarchy server-side, not just in the UI — e.g. an officer's `update` is rejected outright if they try to set `status: "Closed"`; only a citizen's own `isOwnCitizenComplaint()` branch permits that.

## AI integration

Four server-side routes call Gemini (never from the browser, so the API key stays server-only):

| Route | Purpose |
|---|---|
| `/api/classify` | Classifies a citizen's raw complaint text into the `AIClassification` shape, and checks it against nearby open complaints in the same ward (last 30 days) for duplicate consolidation |
| `/api/transcribe` | Takes recorded audio, transcribes it, and auto-detects the spoken language (no language picker needed) |
| `/api/insight` | Given department complaint counts (this 30-day window vs. the last), writes a short analytics narrative for a rep's dashboard |
| `/api/priority-ranking` | Given citizen suggestion counts per ward/category + seeded demographic data, ranks the top 3-5 development priorities with a one-line justification each — **the actual core ask of the brief** |

`/api/insight` and `/api/priority-ranking` results are **cached in Firestore** (`lib/dashboardCache.ts`), keyed by scope + complaint count — a dashboard only calls Gemini again if the underlying complaint data actually changed since the last visit, not on every page load. This was added specifically to protect the Gemini free tier's request-count ceiling, but it's also just the correct behavior (no point regenerating an unchanged insight).

## Sample / seed database

Since this is a 3-day build, three things stand in for production data sources, all clearly callable out as such:

1. **All 28 states + 8 union territories, a few wards each** ([`lib/wards.ts`](./lib/wards.ts)) — 75 wards total, real (approximate) coordinates for every one. Signup, GPS-based ward routing, and constituency grouping genuinely work nationwide today, not just for a couple of pilot states — a citizen anywhere in India auto-matches to their nearest of these 75 wards (plain Haversine distance, no paid Geocoding API). Seeded demo **complaints and demographic data** are concentrated in 3 states — Telangana (Malkajgiri, Uppal, Kapra), Andhra Pradesh (Mangalagiri, Tadepalli, Thullur), and Delhi (Karol Bagh, Chandni Chowk, Dwarka) — so the dashboards have something real to show rather than being thin everywhere; every other state's officer/MLA/MP accounts and citizen routing work identically, they'd just start from an empty queue.
2. **Seeded per-ward demographic dataset** ([`lib/demographics.ts`](./lib/demographics.ts)) — school enrollment, distance-to-nearest-facility, an infra-gap score (0-100), and existing facilities per ward. This stands in for Census/NFHS/data.gov.in in a production version; the priority-ranking feature is built to take real data in the exact same shape later.
3. **Seed scripts** (`scripts/`) create realistic demo data directly in Firestore, bypassing the live Gemini call for seed data (hand-authored classifications) to conserve API quota:
   - `seed-accounts.mjs` — 8 department officers, 2 department heads, 2 MLAs, 1 MP, all fixed credentials (see `DEMO_LOGINS.md`)
   - `seed-complaints.mjs` — ~16 complaints spanning every status, priority, and department, submitted by 3 seed citizen accounts
   - `seed-extra-stuck.mjs` — one complaint deliberately timestamped to demonstrate MP-level escalation live, without waiting real days

Run them with `node scripts/seed-accounts.mjs` then `node scripts/seed-complaints.mjs` against a fresh Firebase project (they read Firebase config from `.env.local`).

## Deployment

Deployed on **Vercel**, not Firebase App Hosting — App Hosting requires the paid Blaze plan with no free tier at all, whereas Vercel deploys this same Next.js app for free directly from GitHub. Firebase itself (Auth + Firestore) is still used exactly as designed; only the hosting layer changed. Every push to `main` redeploys automatically.

## What's explicitly cut (roadmap, not built)

Named here on purpose — scoped honesty was a deliberate choice, not an oversight. Split into two kinds of "not built": things that just need more dev time (free), and things that need an actual budget (paid third-party infra).

**Roadmap — buildable later, no budget needed:**
- **Full multilingual translation** (Cloud Translation API) — voice input already works in multiple languages via Gemini's native multilingual understanding; translating the UI itself is a straightforward follow-on
- **Live Census/NFHS/data.gov.in integration** — the seeded per-ward dataset stands in, built to the same shape
- **Real government-ID SSO for officials** — Firebase email/password stands in; `department`/`constituency` fields already exist on the user record, so swapping the login method later doesn't change the data model
- **Push notifications** for escalation — currently computed at read time only; a citizen/rep must open the dashboard to see it. Could be added without Cloud Functions by having the officer's status-update action also call a notification-send route directly

**What funding unlocks — genuinely needs paid infrastructure, not just engineering time:**
- **Live WhatsApp/SMS intake** — Office Staff can log a complaint received by any of these channels today (tagged with its real `source`), but automatically receiving them requires a WhatsApp Business API account or SMS gateway (Twilio, Gupshup, MSG91) — business verification plus real per-message billing. The `ComplaintSource` type already lists these channels; funding wires up the pipe, it doesn't redesign it.
- **Production-scale infrastructure** — Firebase Blaze, a paid Gemini quota, and dedicated hosting once real citizen volume (not a hackathon demo) starts hitting today's free-tier ceilings.

Already built despite initially looking out of scope: a **demand hotspot map + priority heatmap** (ward-level, color-coded by severity) — it turned out not to need the Google Maps Platform or any billing at all, just our own seeded ward coordinates rendered as an SVG. Also built further than planned: **nationwide ward/state coverage** (all 28 states + 8 union territories, 75 wards) instead of just the original 3 pilot states.

## Testing

Verified end-to-end via automated browser testing (Playwright) for every role's signup/login, the full citizen→officer→citizen resolution loop, ward/constituency-scoped data access (confirmed officers/MLAs/MPs/department heads only ever see their own scope), the priority-ranking panel, and the dashboard caching behavior (confirmed a cache miss on first load, zero API calls on a repeat visit with unchanged data).
